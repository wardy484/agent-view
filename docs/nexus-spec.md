# Nexus-UI — Requirements Specification

> This document is the source of truth for what Nexus-UI must do.
> Every atomic requirement has a stable `REQ-*` ID.
> IDs are **never reused and never renumbered** — traceability depends on it.
>
> Agents and humans close requirements by writing a Pest test whose
> `it('REQ-XXX-NNN: …')` name references the ID. `php artisan spec:check`
> enforces 1:1 correspondence in CI.
>
> See `AGENTS.md` for the 7-step delivery loop.
> See `/Users/kim/.claude/plans/the-prompt-role-you-cozy-goblet.md` for the full
> PRD, architecture, and rationale behind these requirements.

## Phase 0A — Walking Skeleton Deploy

- **REQ-P0A-001** `.env.example` uses Postgres (not SQLite) as the default DB connection.
- **REQ-P0A-002** `.env.example` uses Redis for session, cache, and queue drivers.
- **REQ-P0A-003** `cloud.yaml` exists and defines build + deploy steps for Laravel Cloud.
- **REQ-P0A-004** `.herd.yml` pins the PHP and Node versions the project expects locally.
- **REQ-P0A-005** Laravel Cloud production environment deploys green from `main`.
- **REQ-P0A-006** Laravel Cloud production environment runs `php artisan migrate --force` automatically.
- **REQ-P0A-007** Laravel Cloud queue worker process is declared and running.
- **REQ-P0A-008** No secrets are committed to the repository (`.env` is gitignored; secrets live in Cloud env config).

## M1 — Universal Table

- **REQ-M1-001** MCP tool `present_structured_data` accepts the v1 input schema (workbench_slug, view_type, data_payload, optional snapshot_id, title, metadata).
- **REQ-M1-002** All `/ai/*` routes require a valid Sanctum Bearer token; anonymous requests return 401.
- **REQ-M1-003** `snapshot_versions.revision` is monotonic (1, 2, 3…) and unique per `snapshot_id`.
- **REQ-M1-004** `present_structured_data` response contains `structuredContent`, a text content part with the workbench URL, and a `text/html` resource content part.
- **REQ-M1-005** Table view component renders every row in `data_payload.rows` using columns from `data_payload.columns`.
- **REQ-M1-006** TanStack Table performs filter, multi-column sort, and pagination client-side with zero network calls.
- **REQ-M1-007** The version switcher lists every revision of a snapshot, newest first, and navigates to the selected revision.
- **REQ-M1-008** `TableViewSchema::validate()` rejects payloads missing `columns` or `rows` with a clear error.
- **REQ-M1-009** `SnapshotVersioning::append()` is the only writer to `snapshot_versions`; direct model writes are disallowed by a test.
- **REQ-M1-010** A newly-created snapshot has `current_version_id` equal to its first version; appending a version updates `current_version_id`.
- **REQ-M1-011** `TablePreviewRenderer` produces HTML ≤ 64 KB, truncates to 50 rows, and shows a "showing 50 of N" footer when truncation occurred.
- **REQ-M1-012** `preview_html` is cached on the `snapshot_versions` row at write-time; repeated reads never re-render.
- **REQ-M1-013** Users can mint a Sanctum personal access token in `/settings/tokens` scoped to a `workbench_slug`.
- **REQ-M1-014** The workbench page URL returned by the tool resolves to a page that renders the table in the browser.

- **REQ-M3-010** `SnapshotController` exposes a `mode` Inertia prop equal to `"preview"` when the request has `?mode=preview` or no authenticated user, and `"app"` otherwise; an `isAuthenticated` boolean prop reflects the auth state.
- **REQ-M3-011** The `ui://` resource emitted by `present_structured_data` carries `?mode=preview` on the iframe-embeddable URL so mcp-ui clients render snapshots without the app shell.
- **REQ-M3-012** The `snapshot` page renders inside the app sidebar layout when `mode === "app"` and renders bare (no sidebar, no workbench header) with a subtle floating home link when `mode === "preview"`.
- **REQ-M3-013** In-app mode shows a fullscreen toggle button in the snapshot header; activating it hides the workbench header and surfaces the same floating home link, and the Escape key restores the chrome.

## M4 — Sharing

- **REQ-M4-000** `workbenches` gains a nullable `owner_user_id` foreign key to `users` (`nullOnDelete`). When `PresentStructuredData` runs under Sanctum web auth (`auth()->user()` present), it sets `owner_user_id` on workbench creation. When it runs under the unauthenticated local stdio server, `owner_user_id` stays null and the workbench is treated as system-owned (never shareable). A one-shot data migration back-fills existing rows from the earliest `mcp_call_logs` entry whose `user_id` is non-null. Sharing policies (REQ-M4-005) reject every workbench whose owner is null. Once set to a non-null user, `owner_user_id` never changes except via an explicit transfer action (out of scope for M4).
- **REQ-M4-001** Snapshots carry a `visibility` enum with values `private` (default), `link`, and `shared`. Visibility is stored on the `snapshots` row, not the workbench. A viewer always sees the snapshot's **latest** revision (resolved via `current_version_id` at request time); earlier revisions remain hidden to non-owners.
- **REQ-M4-002** When `visibility = link`, the snapshot has a 32-byte URL-safe random `share_token` (unique, indexed). Route `GET /s/{token}` resolves to the read-only snapshot view without authentication. Flipping visibility to `private` clears the token; re-enabling `link` mints a fresh token. The route is rate-limited and every hit writes a `snapshot_share_accesses` audit row.
- **REQ-M4-003** Table `snapshot_shares` with columns `id`, `snapshot_id`, `email` (lowercased, indexed), `user_id` nullable, `granted_by_user_id`, `created_at`, `revoked_at` nullable. Unique `(snapshot_id, email)` where `revoked_at IS NULL`.
- **REQ-M4-004** Sharing a snapshot by email: if a `User` with that email exists, `user_id` is populated immediately and a `SnapshotSharedNotification` is queued. If no user exists, the row is created with `user_id = null` and an invite email with a signup link is sent; Fortify's `CreateNewUser` back-fills `user_id` on any matching `snapshot_shares` rows during registration.
- **REQ-M4-005** `SnapshotPolicy@view` grants read access when any of the following is true: the user owns the workbench; `visibility = link` and the request presents the valid `share_token`; `visibility = shared` and an unrevoked `snapshot_shares` row matches the authenticated user's id or email. Revoking sets `revoked_at` (soft — never hard-deleted).
- **REQ-M4-006** The shared snapshot view is strictly read-only: version switcher is hidden (latest-only per REQ-M4-001), the "Send back to Agent" control is hidden for public-link viewers, and all mutation affordances (rename, delete, re-share) are gated by ownership.
- **REQ-M4-007** Signed-in users see a dedicated **Shared with me** sidebar section listing every snapshot where they hold an unrevoked `snapshot_shares` row (resolved by `user_id` or email). Owner sidebars display a share-count badge on snapshots with active shares or an active `share_token`.
- **REQ-M4-008** MCP writes (`present_structured_data`) remain owner-only regardless of share state; shares grant read access only. `get_follow_up_context` is scoped to the caller's Sanctum token, so each viewer's selections are visible only to that viewer's agent — never to the owner or other viewers.
- **REQ-M4-009** `Snapshot::shareToken()` rotation and `snapshot_shares` revocation both invalidate any cached access decisions within one request cycle (no stale policy cache).
- **REQ-M4-010** Owner-facing **Share** control on the snapshot page header. Rendered only when `is_owner && !is_public_link`. Opens a dialog that surfaces three visibility modes (Private / Anyone with link / Specific people), the current `/s/{token}` URL with a copy button when link mode is active, and an email input plus revoke-able list of current shares when shared mode is active. All four mutation endpoints (`PATCH .../visibility`, `POST .../share-token/rotate`, `POST .../shares`, `DELETE .../shares/{share}`) live under the authenticated snapshot route prefix and reject any non-owner caller with 403. The dialog reads the current state from `shares` and `share_url` props included on the snapshot show payload (owners only).

## M5 — Report

- **REQ-M5-000** `view_type = "report"` is registered end-to-end: the `present_structured_data` MCP tool accepts it, the React snapshot dispatcher (`resources/js/pages/snapshot.tsx`) routes it to the report renderer, and the dashboard (`resources/js/pages/dashboard.tsx`) lists it under a `narrative` zone alongside the four structured zones. Unknown-view-type fallback behaviour is preserved for any future type.
- **REQ-M5-001** `ReportViewSchema::validate()` accepts `{ blocks: [...] }` where each block is a discriminated union: `{type: "markdown", body: string}` (markdown prose) or `{type: "embed", snapshot_id: int}` (embedded snapshot). Blocks is a non-empty array; validation throws `ReportViewSchemaException` with dot-path messages (e.g. `data_payload.blocks[3].snapshot_id is required and must be an integer.`).
- **REQ-M5-002** Embeds are same-workbench only and cannot target another report. The MCP tool resolves each `snapshot_id` in the payload against the target workbench; mismatched-workbench embeds and embeds whose target snapshot currently has `view_type === "report"` are rejected with a dot-path error before any `snapshot_versions` row is written.
- **REQ-M5-003** Revision pinning on write. When `SnapshotVersioning::append()` persists a `report` view, every embed block is rewritten so that `snapshot_version_id` is materialised to the embedded snapshot's `current_version_id` at the moment of append. The pin is frozen for that report revision; a later report revision re-pins at that point in time. The write also populates a `snapshot_embeds` denorm row per (report_snapshot_id, report_revision, embedded_snapshot_id, embedded_snapshot_version_id).
- **REQ-M5-004** `SnapshotPolicy@view` grants transitive read access to an embedded snapshot when the caller can view at least one report whose **latest** revision embeds that snapshot. Works for owner viewers, `snapshot_shares` recipients, and valid `share_token` link viewers on the report. Revoking the report share, or a later report revision dropping the embed, automatically revokes transitive access on the next request (no materialised share rows to clean up).
- **REQ-M5-005** MCP writes remain owner-only regardless of transitive read access — a viewer who can read an embedded snapshot only because a report transitively granted access cannot call `present_structured_data` against that snapshot's workbench. M4-008 stands untouched.
- **REQ-M5-006** `ReportPreviewRenderer::render()` emits HTML that renders markdown blocks as escaped prose and embed blocks as summary cards (title + view_type badge + truncated child preview HTML). Enforces the existing 64 KB byte cap by allocating `floor((65536 - markdown_bytes) / count(embed_blocks))` per embed and truncating child preview HTML to fit; oversize output carries a `data-truncated="true"` footer. The root wrapper is `<div data-nexus-preview="report">`.
- **REQ-M5-007** The snapshot page data loader (`SnapshotController@show`) resolves every embed in a `report` version at read time: loads the pinned `SnapshotVersion`, runs `SnapshotPolicy@view` per embed, and inlines `{view_type, payload, version_id, title, pinned_revision, current_revision, restricted}` per embed block into the Inertia props. Policy-denied embeds (rare given REQ-M5-004) reduce to `{type: "embed", restricted: true}`; deleted embed targets produce the same `restricted` shape. Markdown blocks pass through unchanged.
- **REQ-M5-008** `resources/js/components/nexus/report-view.tsx` renders blocks in order: markdown via the shared markdown pipeline (reused from `slide-deck-view.tsx`), embeds via the existing `TableView` / `KanbanView` / `FlowchartView` / `SlideDeckView` components inside a read-only wrapper. Each embed card displays a "v{pinned} · current v{latest}" badge that links to the embedded snapshot in a new tab, a `Restricted embed` placeholder when `restricted = true`, and disables selection / send-to-agent affordances inside report mode for M5.

## M6 — Comments on Markdown

> Adds inline review comments to the `report` view. Scope is markdown blocks
> only — embed blocks and other view types are explicitly out of scope and
> will get their own milestone if/when needed. Comments live on the snapshot
> (not a specific revision) and re-anchor per-version via a hybrid offset +
> quote/prefix/suffix model so they survive agent edits and surface as
> `stale` when the anchor text disappears.

- **REQ-M6-001** Report markdown blocks gain a stable `id` field (UUID v4). `ReportViewSchema::validate()` accepts blocks with or without `id`; missing IDs are auto-assigned by the validator. On a subsequent revision, the validator carries forward an `id` from the previous version's block when the new block's `body` sha1 matches an existing block's `body` sha1 (best-effort stability for agents that don't supply IDs). Agents are encouraged but not required to round-trip the IDs they receive.
- **REQ-M6-002** `snapshot_embeds.block_index` is replaced by `block_id` (FK-style reference into the report payload, not a real FK). Migration back-fills `block_id` for existing rows by reading each report version's payload, assigning UUIDs, and rewriting `data_payload`. Subsequent embed pin lookups use `block_id` exclusively; `block_index` column dropped.
- **REQ-M6-003** Table `comments` with columns: `id`, `snapshot_id` (FK), `block_id` (uuid, indexed), `parent_comment_id` (nullable self-FK for replies), `kind` enum `{comment, suggestion}`, `body` (text), `proposed_text` (text, nullable; required when `kind = suggestion`, must be null otherwise), `anchor_quote`, `anchor_prefix`, `anchor_suffix`, `anchor_start_hint` (int), `anchor_end_hint` (int), `status` enum `{open, resolved, stale, wontfix}` default `open`, `resolution` enum `{user, agent}` nullable, `created_on_version_id` (FK, immutable), `addressed_on_version_id` (FK, nullable), `author_user_id` (FK), `author_kind` enum `{user, agent}` default `user`, `created_at`, `updated_at`, `deleted_at`. Replies (rows where `parent_comment_id IS NOT NULL`) have all anchor columns null and `kind = comment`; a CHECK constraint enforces both. Replies cannot themselves have replies (CHECK on `parent_comment_id` chain depth = 1).
- **REQ-M6-004** `App\Nexus\Comments\AnchorResolver::resolve(Comment $c, SnapshotVersion $v): ResolvedAnchor` returns one of: `{status: open, block_id, start, end}` when the block exists in `$v.data_payload` and `anchor_quote` is found unambiguously (using `start_hint..end_hint` first, then `anchor_quote` substring search disambiguated by `anchor_prefix` / `anchor_suffix`), or `{status: stale, reason}` when the block is missing, the quote no longer occurs, or multiple matches remain ambiguous after prefix/suffix disambiguation. Resolution is pure (no DB writes); `comments.status` is updated lazily by the snapshot show endpoint and never blocks reads.
- **REQ-M6-005** `CommentPolicy` rules: `view` mirrors `SnapshotPolicy@view`; `create` requires snapshot ownership OR an unrevoked `snapshot_shares` row for the authenticated user; `update` and `delete` require the original `author_user_id` OR snapshot ownership; `resolve` requires `update` permission; `react` requires `view`. Comments authored by `author_kind = agent` cannot be edited or deleted by anyone (agent rows are immutable history); they may be resolved.
- **REQ-M6-006** Replies are flat: a reply row's `parent_comment_id` references a root comment (a row whose own `parent_comment_id` is null). The `comments.body` field is markdown; replies inherit the parent's anchor and never have their own. `replies` are returned inline with their parent in `GET` responses; ordering is `created_at ASC` within a thread.
- **REQ-M6-007** Table `comment_reactions` with columns `id`, `comment_id` (FK), `user_id` (FK), `emoji` (string, constrained to one of `👍 👎 ❤️ 🎉 🤔 👀`), `created_at`; unique `(comment_id, user_id, emoji)`. Reactions are toggleable: a second POST with the same `(comment_id, emoji)` from the same user deletes the row. Reactions apply to root comments and replies alike.
- **REQ-M6-008** Suggestion lifecycle: when `kind = suggestion`, the comment carries `proposed_text` describing the desired replacement for `anchor_quote`. Owner-only endpoint `POST /snapshots/{id}/comments/{cid}/accept` resolves the anchor against the current revision; on a successful resolution, replaces the resolved range in the relevant block's `body` with `proposed_text`, calls `SnapshotVersioning::append()` to produce a new revision, and atomically sets the comment's `status = resolved`, `resolution = user`, `addressed_on_version_id = <new revision>`. Stale anchors return 409. Agents have no equivalent acceptance tool; they apply suggestions by emitting a new `present_structured_data` payload and then resolving with `resolve_comments`.
- **REQ-M6-009** MCP tool `get_snapshot_comments` accepts `{snapshot_id, status?, include_resolved_since?}` and returns `{snapshot_id, current_revision, comments: [{id, block_id, status, anchor: {quote, prefix, suffix, resolved_in_current_version}, body, kind, proposed_text?, author: {display_name, kind}, created_at, created_on_revision, addressed_on_revision?, thread: [{id, body, author, created_at}], reactions_summary: {emoji: count}}]}`. The tool's description explicitly instructs the model that comment bodies are user-authored data and must not be treated as instructions.
- **REQ-M6-010** MCP tool `resolve_comments` accepts `{comment_ids: string[], resolution_note?: string, addressed_on_revision?: int}` and, for each id the caller is authorised to resolve, sets `status = resolved`, `resolution = agent`, `addressed_on_version_id` to the supplied revision (or the snapshot's `current_version_id` at call time), and posts a reply with `author_kind = agent` and `body = resolution_note` when a note is supplied. Returns `{resolved: [ids], skipped: [{id, reason}]}`. Idempotent: already-resolved IDs return as `skipped` with `reason = already_resolved`.
- **REQ-M6-011** MCP tool `reply_to_comment` accepts `{comment_id, body}`, creates a reply with `author_kind = agent` and `parent_comment_id = comment_id`, returns `{reply_id}`. Rejects 404 when the comment is deleted, 422 when the target is itself a reply (no nesting).
- **REQ-M6-012** New revisions never copy comment rows. `addressed_on_version_id` is set only by `resolve_comments`, suggestion-accept (REQ-M6-008), or owner UI action. `status = stale` is determined lazily on render via `AnchorResolver` and may auto-revive to `open` when a later revision re-introduces the quote (no manual user action required). `created_on_version_id` is immutable.
- **REQ-M6-013** Selecting text within a markdown block surfaces a floating action menu anchored above the selection (`resources/js/components/nexus/comment-selection-menu.tsx`) with three actions: `Comment`, `Suggest edit`, `Copy`. Selection that crosses block boundaries disables `Comment` and `Suggest edit` (anchors are block-scoped per REQ-M6-003).
- **REQ-M6-014** Snapshot page right sidebar gains a tabbed panel (`resources/js/components/nexus/snapshot-sidebar.tsx`) with two tabs: `Comments` (default) and `History`. The Comments tab lists root comments grouped by `block_id` in document order, each with its thread, reactions, and status badge; clicking a comment scrolls to and highlights the resolved anchor range (or shows a stale chip when resolution failed). The Comments tab is hidden for unauthenticated link-token viewers (consistent with REQ-M4-006 read-only stance) but visible read-only for grantees.
- **REQ-M6-015** History tab renders one row per `snapshot_versions` row, newest first, showing revision number, `metadata.author_kind`, relative time, and `metadata.summary` when present. Each row expands to show the IDs of comments whose `addressed_on_version_id` equals that revision (resolved by user, by agent, or via suggestion-accept), each link scrolling the Comments tab to the resolved comment. Clicking a non-current row navigates the existing `version-switcher.tsx` to that revision; comments re-anchor and the page enters read-only mode (no new comments on historical versions).
- **REQ-M6-016** `GET /snapshots/{id}/sidebar?since=<cursor>` returns delta `{comments_revision, current_revision, comments: [...] }` where `comments_revision` is a monotonic counter on the `snapshots` row incremented on any comment / reply / reaction / resolution write. Inertia partial reload uses `router.reload({ only: ['comments', 'currentRevision'] })` on an 8-second interval gated by `document.visibilityState === 'visible'`. Polling stops when the tab is hidden and resumes on focus.
- **REQ-M6-017** Comment create, reply create, reaction toggle, and status flips render optimistically client-side using Inertia v3 optimistic updates with automatic rollback on server rejection. Optimistic rows carry a temporary client UUID and are reconciled with the server-issued ID on success.
- **REQ-M6-018** When polling detects a `current_revision` greater than the rendered one, the snapshot page displays a non-disruptive top banner ("Agent pushed v{n} · view changes") that does not auto-swap content; clicking the banner navigates to the new revision. The banner pulses once on appearance and dismisses on click or tab blur.
- **REQ-M6-019** Stale comments (REQ-M6-004) render in the sidebar with a muted style, an `Anchor lost` chip, and the original `anchor_quote` shown verbatim; their `Reply` and `React` actions remain enabled, `Resolve` and `Accept` are disabled. A stale comment that auto-revives (per REQ-M6-012) silently returns to its normal style on the next render.
- **REQ-M6-020** On screens narrower than `lg` (Tailwind's 1024px breakpoint), the snapshot sidebar from REQ-M6-014 is no longer rendered inline below the report. Instead, the snapshot page header gains a "Comments" trigger (count badge when there are open comments on the snapshot) that opens the existing `<SnapshotSidebar>` content inside a slide-in sheet/drawer anchored to the right edge. The drawer slides in/out at the same breakpoint without remounting any state. Above `lg`, the layout is unchanged: the sidebar renders inline as a fixed-width column to the right of the report.
- **REQ-M6-021** Below Tailwind's `lg` breakpoint, the floating selection menu from REQ-M6-013 is replaced by a sticky bottom toolbar (`resources/js/components/nexus/comment-selection-toolbar.tsx`) that surfaces whenever a non-collapsed selection exists inside a markdown block. The toolbar offers the same three actions — Comment, Suggest edit, Copy — and disables Comment + Suggest when the selection crosses block boundaries. The toolbar slides up on selection and slides down on selection clear or Escape. Above `lg`, the existing floating menu is unchanged. Additionally, `useMarkdownSelection` listens for `selectionchange` and `pointerup` events so touch selections register on iOS/Android. Superseded by REQ-M6-023 — the sticky bottom toolbar is replaced by a floating pill that positions below the selection on mobile.
- **REQ-M6-022** Below Tailwind's `lg` breakpoint, the comment selection toolbar from REQ-M6-021 is always visible: it is permanently sticky at the viewport bottom, full width, and never slides off-screen. When no selection is active it renders a muted "Highlight text to comment" empty state with all action buttons in a `disabled` / `aria-disabled` state. When a selection is detected the buttons enable, and Comment / Suggest read the live `window.getSelection()` at click time via a shared `captureSelection` helper rather than from React state — eliminating the selection-event timing race that previously suppressed the toolbar on Android Chrome / iOS Safari (where `selectionchange` fires many times during a touch drag and any collapsed snapshot raced the late-arriving valid selection). The selection helpers (`findBlockAncestor`, `offsetWithinBlock`, `captureSelection`) live in `resources/js/lib/selection-helpers.ts` and are shared between `useMarkdownSelection` and the toolbar. The hook's prior 50ms `setTimeout` debounce is replaced by a `requestAnimationFrame` coalesce. The report column gains `pb-20 lg:pb-0` so the always-visible toolbar (~72px tall plus safe-area inset) never covers the last paragraph. The desktop floating menu from REQ-M6-013 is unchanged above `lg`. Superseded by REQ-M6-023 — the sticky bottom toolbar is replaced by a floating pill that positions below the selection on mobile.
- **REQ-M6-023** Selection actions surface as a compact floating pill (`resources/js/components/nexus/comment-selection-pill.tsx`) anchored to the selection's bounding rect. On screens ≥ Tailwind `lg`, the pill renders ABOVE the selection (existing desktop behaviour from REQ-M6-013). On screens < `lg`, the pill renders BELOW the selection (avoiding the OS-rendered selection bubble that sits above the highlight on Android Chrome / iOS Safari). The pill contains three icon-only buttons (Comment, Suggest edit, Copy) ~40px tall, ~120px wide; cross-block selections disable Comment + Suggest. The pill mounts only when there is a non-collapsed selection inside the report container; it auto-hides on scroll (the selection rect goes stale on scroll, so the pill clears the selection — matching Medium / Notion behaviour). - **REQ-M6-025** A one-shot data migration walks every `snapshot_versions` row whose `view_type = 'report'` and assigns a UUID v4 `id` to every block in `data_payload.blocks` that lacks one. The migration writes via `SnapshotVersion::query()->update(['data_payload' => ...])` to amend the existing revision in place — the documented exception to the SnapshotVersioning rule, mirroring REQ-M6-002's back-fill. Snapshots whose blocks already carry ids are skipped. The migration is idempotent. Without this back-fill, snapshots created before REQ-M6-001 shipped have blocks without `id`, the frontend's `data-comment-block-id` attribute is dropped, and the floating selection pill never mounts so comments are unusable on those legacy snapshots.
- **REQ-M6-026** `SnapshotController@show` projects `data_payload.blocks` through `resolveReportBlocks()` before passing them to Inertia as `version.data_payload.resolved_blocks`. That projection must forward every block's `id` field to the frontend (alongside `type` / `body` for markdown and the embed metadata for embeds). Without this forwarding the React `<MarkdownBlockView id={block.id}>` always receives `undefined`, the rendered DOM never carries a `data-comment-block-id` attribute, `findBlockAncestor` returns null, and the comment selection pill never mounts — making comments silently unusable end-to-end regardless of whether the underlying payload (REQ-M6-001) and back-fill (REQ-M6-025) carry ids correctly. Embed projections also forward `id` (M6 v1 only scopes comments to markdown blocks, but block ids are stable identifiers that other anchored features will need). Legacy markdown blocks that genuinely lack an `id` in the stored payload project as `id: null` until REQ-M6-025's back-fill runs.

The expanded pill grows in height to host a textarea (and a second "proposed text" textarea for Suggest), a Submit and a Cancel button, while keeping the same anchor position relative to the selection. The selected text remains visually highlighted (a `<mark data-pending-anchor>` wrapping the range) for as long as the composer is open; closing the composer (Submit, Cancel, Escape) removes the synthetic highlight and clears the selection. The expanded pill cannot exceed the viewport's smaller dimension and stays clamped inside. Submit POSTs to `/snapshots/{snapshot}/comments` (the existing REQ-M6-014 endpoint) and reloads only the `comments` Inertia prop on success; failure keeps the composer open with an inline error and preserves the synthetic mark. The selection helpers gain `synthesizeHighlight(range)` and `removeSyntheticHighlight()` exports so the pill can manage the synthetic `<mark>` outside React's render tree.
- **REQ-M6-028** Every comment in the snapshot's `comments` Inertia prop whose `anchor.resolved_in_current_version === true` renders its `anchor.quote` as a persistent inline highlight inside the relevant markdown block. A new `resources/js/components/nexus/comment-highlight-overlay.tsx` component walks the rendered report container in a `useLayoutEffect` and wraps each resolved anchor in a `<mark data-comment-id="{id}" data-status="{status}" data-comment-overlay="true">` element. Highlights are styled by status: `open` → yellow tint (`bg-yellow-200/40 dark:bg-yellow-900/40`), `resolved` → muted slate tint with line-through (`bg-slate-300/40 dark:bg-slate-700/40 line-through decoration-slate-500`), `wontfix` → grey tint with strike (`bg-zinc-300/30 dark:bg-zinc-700/30 line-through opacity-60`), `stale` → not rendered (the anchor doesn't resolve, so there is nothing to mark). Hovering a highlight surfaces a shadcn Tooltip with the comment author's display name and the first line of the body; clicking it opens the comment in the sidebar (existing scroll behaviour) AND scrolls the sidebar to that comment row. The overlay is idempotent on every `comments`-prop change: existing `data-comment-overlay="true"` marks are unwrapped before re-walking. Highlights are non-interactive otherwise — they don't suppress text selection, so the pill from REQ-M6-027 still works on top of them.
- **REQ-M6-029** Inside the inline comment composer (REQ-M6-027), pressing ⌘+Enter (Mac) or Ctrl+Enter (Windows/Linux) submits the comment, equivalent to clicking Submit. The Submit button shows the active shortcut next to its label as a small `<kbd>` hint (e.g. `Submit ⌘↩` on Mac, `Submit Ctrl+↵` elsewhere) — the platform is detected at render time via `navigator.platform` (with `userAgent` as fallback). The keydown handler is scoped to the composer's textarea(s) so the binding does not trigger globally on the page. New helpers `isMac()`, `metaKeyLabel()`, and `metaKeyShortcutLabel()` live in `resources/js/lib/platform.ts`. The `<kbd>` hint is greyed out (reduced opacity) whenever the Submit button is in its disabled state (empty body, or empty proposed text on a suggestion).

- **REQ-M6-030** The "create new root comment" composer in the snapshot sidebar (`resources/js/components/nexus/snapshot-sidebar.tsx`) is removed. The floating pill (REQ-M6-027 inline composer) is the sole authoring surface for new root comments. The sidebar continues to host the comment list, reply boxes, reactions, status controls, and the historical-view banner — only the root-comment composer block (and the `composerSelection` plumbing on the Comments tab) is excised. The sidebar's `Props` no longer accept a `composerSelection` (or `onComposerClose`); the snapshot page no longer threads selection through the sidebar.
- **REQ-M6-031** The floating pill (REQ-M6-027) gains a fourth icon-only action **Delete** (lucide-react `Trash2` icon) rendered after Comment / Suggest edit / Copy. Tapping Delete creates a `kind = suggestion` comment with `proposed_text = ''` (an empty string represents deletion of the selected text). UI confirmation is implicit — the pill collapses immediately on submit (no expanded composer is shown for Delete). Cross-block selections disable Delete with the same tooltip (`Selection must stay within one block.`) used by Comment + Suggest. `readOnly` (historical view) also disables Delete with the read-only hint. The button has `data-testid="comment-selection-pill-delete"`. - **REQ-M6-032** The pill's Suggest-edit composer drops the secondary "comment body" textarea — only the `proposed_text` textarea is rendered. The `body` of the resulting Comment row is set to a fallback empty string (`''`). The migration's `body text NOT NULL` constraint accepts an empty string (only `NULL` is rejected), and `CommentController@store` validation is relaxed for `kind=suggestion` so an empty/missing `body` is acceptable; the controller substitutes `''` if absent. `proposed_text` continues to carry the actual content of the change.
- **REQ-M6-033** Persistent comment highlights (REQ-M6-028) render with status- AND kind-aware styling. `kind = comment, status = open` keeps the existing yellow tint. `kind = suggestion, status = open` AND `proposed_text !== ''` paints with an indigo tint (`bg-indigo-200/40 dark:bg-indigo-900/40`). `kind = suggestion, status = open` AND `proposed_text === ''` (a deletion) paints with a red tint and line-through (`bg-red-200/40 line-through decoration-red-500`). Resolved/wontfix variants follow the existing muted slate / grey strike pattern (regardless of kind). Tooltips include the comment's kind alongside the existing author + first-line content (e.g. `Alice (suggestion): Replace this with…`). The overlay component grows a small helper `isDeletion(comment)` returning `comment.kind === 'suggestion' && comment.proposed_text === ''` and branches styling on it. Both `kind` and `proposed_text` are surfaced through the `HighlightCommentSummary` shape.
- **REQ-M6-034** The pending-anchor synthetic highlight (REQ-M6-027) and the persistent overlay highlights (REQ-M6-028) both survive page scroll. The pill's scroll listener (introduced in REQ-M6-023, which clears the selection on scroll to mimic Medium / Notion) is restricted to `mode === 'idle'` only — when actively composing a comment or suggestion, scroll must NOT call `onClose()` or tear down the synthetic mark. Persistent overlay highlights remain in place across scroll because the overlay's `useLayoutEffect` only re-runs on `comments`-prop / container-ref / click-handler changes, never on scroll events; the dependency array of that effect contains exactly `[comments, containerRef, onCommentClick]` and contains no scroll-derived state.
- **REQ-M6-035** Highlight wrapping (both the persistent overlay from REQ-M6-028 and the pending-anchor synthetic mark from REQ-M6-027) MUST NOT alter the document's layout. When a comment's anchor range spans multiple text nodes or element boundaries (across `<code>`, `<strong>`, paragraph boundaries, or sibling inline elements), the overlay walks the range and emits one `<mark>` per text node sub-range — each wrap is a pure text-node split + parent-equivalent inline wrap that introduces no block-level elements, no extra whitespace, and no `display` overrides. Wrapping a paragraph-spanning quote produces multiple inline `<mark>` elements that share the same `data-comment-id` (so click handlers and tooltips remain uniform), never a single `<mark>` containing non-text children that would force the contained content into a new block. The shared algorithm is exposed from `resources/js/lib/selection-helpers.ts` as `wrapRangeWithMarks(range, factory)` and `unwrapMarks(root, selector)`, used by both `comment-highlight-overlay.tsx` (persistent) and `synthesizeHighlight` / `removeSyntheticHighlight` (pending). No call site uses `range.surroundContents()` or `range.extractContents()` for highlight wrapping. `removeSyntheticHighlight` unwraps every `[data-pending-anchor]` element and calls `parent.normalize()` to coalesce adjacent text nodes back together.
- **REQ-M6-036** Persistent comment highlights from REQ-M6-028 are applied on the snapshot's first paint, before any user interaction. The overlay observes the report container for child mutations (via a `MutationObserver` watching `childList` and `subtree` on the container) so that wrapping is retried whenever react-markdown commits new descendants. The observer is created on mount, fires the wrap pass once on initial connection (in case markdown is already there), debounced to one re-wrap per animation frame via `requestAnimationFrame`, and is torn down on unmount or when the comments prop changes (the existing `useLayoutEffect` re-run still drives the unwrap-then-rewrap cycle on data changes). To avoid a feedback loop where the overlay's own DOM mutations re-trigger the observer, the observer is briefly disconnected before each wrap pass and reconnected after.
- **REQ-M6-037** The persistent comment highlights established by REQ-M6-028 / REQ-M6-033 use higher-contrast tints so they are immediately visible to users on both light and dark backgrounds. Concretely, `classForComment` in `resources/js/components/nexus/comment-highlight-overlay.tsx` returns saturated tints at ≥60% opacity (for `comment` kind: `bg-yellow-200/70 dark:bg-yellow-700/40`; for `suggestion` kind, non-deletion: `bg-indigo-200/70 dark:bg-indigo-900/50`; for deletion: `bg-red-200/70 dark:bg-red-900/60` plus `line-through decoration-red-500`; for `resolved`: `bg-slate-300/60 dark:bg-slate-700/60` plus `line-through decoration-slate-500`; for `wontfix`: `bg-zinc-300/50 dark:bg-zinc-700/50` plus `line-through opacity-70`). Every highlight class also includes a 2px dotted bottom border (`border-b-2 border-dotted border-<colour>-400/500`) so the highlight remains recognisable on screens where the background tint blends with the page (e.g. cream / off-white themes). The class strings are emitted as full literal Tailwind tokens so the JIT compiler picks them up at build time.

- **REQ-M6-038** Persistent comment highlights are guaranteed to render on first paint via three complementary triggers, applied in priority order: (a) immediate synchronous wrap inside `useLayoutEffect` after react-markdown's children have mounted, (b) `requestAnimationFrame` retry on the next paint, (c) `setTimeout` polling every 250ms for up to 5 seconds OR until at least one wrap succeeds, whichever comes first. The MutationObserver is retained as a long-lived re-trigger for any subsequent DOM mutations (e.g. polling reloads). The poll halts immediately once any wrap is applied.

> Closes four gaps that prevent a Nexus kanban from being a usable live source
> of truth for the `/feature` orchestrator skill: stable card IDs across
> revisions, real-time UI updates over Reverb, an orchestrator metadata blob
> that survives resume, and richer card fields (link, status, assignee). The

- **REQ-M7-001** `KanbanViewSchema::validate()` auto-assigns a UUID v4 `id` to any card that omits one, and on a subsequent revision of the same snapshot carries forward an `id` from the previous version's card by matching first on explicit `id`, then on `(column_key, title)` tuple. Carry-forward is best-effort; agents that round-trip the IDs they receive get reliable stability. The validator's return value exposes the resolved IDs so callers can persist them. Empty `cards` arrays remain legal.
- **REQ-M7-002** `App\Nexus\SnapshotVersioning::append()` broadcasts a `SnapshotVersionAppended` event on the private channel `snapshot.{snapshot_id}` after the new `snapshot_versions` row is written and `current_version_id` is bumped. The blob is not rendered in any UI but is returned verbatim by `SnapshotController@show` and the MCP `get_snapshot_comments` / snapshot read paths so that resume can reconstruct full state. Schema validation accepts any JSON-serialisable shape; size capped at 32 KB serialised. The orchestrator owns its own contract for the blob's structure.
- **REQ-M7-005** `KanbanViewSchema` accepts three optional card fields, all back-compatible: `link_url` (string URL — must pass `filter_var(FILTER_VALIDATE_URL)`), `status` (enum `ok|warn|error`), and `assignee` (string, ≤64 chars). None of the new fields participate in carry-forward matching (REQ-M7-001 still keys on `id` first, then `(column_key, title)` only).
- **REQ-M7-006** `resources/js/components/nexus/kanban-view.tsx` renders the new card fields: `link_url` makes the card title an `<a target="_blank" rel="noopener">`, `status` drives a 4 px left border stripe coloured green / amber / red for `ok` / `warn` / `error`, and `assignee` renders as a small chip in the card footer. ## Requirement ID Rules

1. **Format**: `REQ-<scope>-<nnn>` where scope ∈ `{P0A, P0B, M1, M2, M3, M4, …}` and `nnn` is a zero-padded 3-digit number.
2. **Stability**: once issued, an ID's text may be refined but its number is frozen forever.
3. **One test per ID**: any Pest `it(…)` name must match the regex `/REQ-[A-Z0-9]+-\d{3}/` to count.
4. **Additions require a spec PR**: if a requirement is missing, add it here before writing code.
